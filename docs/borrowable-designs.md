# ForgeKernel 中值得借鉴的设计（域无关提炼）

> 目的：从 ForgeKernel 的实现里提炼**可迁移到其它域**的设计原则。ForgeKernel 本身做的是
> "用强模型（Teacher）蒸馏弱模型（Student）去把 GPU kernel 写快"，但本文只关心**那些换掉
> GPU 这个 domain 之后依然成立**的结构性设计。每条都附"在 ForgeKernel 里怎么落地"与
> "抽象后的一般形态"，便于把它复用到任何"强模型蒸馏弱模型做探索"的任务。
>
> 依据：`docs/design/milestone-distillation.md`、`docs/design/v1-launch.md`、
> `docs/milestones-template.md`、`docs/kb-harvest.md`、`docs/correctness-monitor.md`，
> 以及 `src/forgekernel/` 下的 `inner/trajectory.py`、`meta_trajectory.py`、`resume/`。

---

## 0. 一句话

ForgeKernel 真正值得借鉴的不是"用 LLM 写 kernel"，而是它把这件事**工程化**的四副骨架：

1. **双环同构**——内环改*产物*，外环改*策略*，两环结构对称；
2. **泄漏红线 L0/L1**——用机械约束保证"可泛化"，而非靠自觉；
3. **机械摘要 + 结构化轨迹**——不让 LLM 去压缩"要喂给 LLM 的东西"；
4. **失败归因到正确产物层**——G/R 分类 + 时间相关成本 + 死胡同表 + 前缀复用。

下面逐条展开，最后给"抽象成通用框架"的模块划分。

---

## 1. 双环同构（内改产物、外改策略）

### 在 ForgeKernel 里
一个 run 有**两个嵌套的循环**，且刻意做成**同构**：

| 维度 | 内环 = student loop | 外环 = meta loop |
|---|---|---|
| 优化对象 | kernel 代码 | 每算子的 **milestone（课程）** |
| 指标 | latency / MFU（各 shape 几何平均） | 学生复现参照性能的程度 |
| 固定输入（决策图） | 每算子 milestone | **meta-milestone（策略）** |
| 诊断信号 | NCU profile | **整条内环轨迹**（轮次记录 + NCU + git log + 曲线平滑度） |
| 剧本 | NCU 症状 → 代码修复 | 轨迹症状 → 课程修改 + KB 示例 |
| 死胡同表 | 性能回归 | 课程改动回归 |
| R0 纪律 | 一次一个最小改动，NCU 门控 | 一次一处最小课程编辑，迁移门控 |
| 一次迭代单位 | 一个决策 Dx.y | 一处课程缺陷修复 |

外环的"NCU"就是内环留下的轨迹——**内环的产出正是外环的诊断输入**。

### 抽象后的一般形态
任何"优化-评估"系统都可套这层双环：
- **内环**：按策略改进**产物**，记录结构化轨迹 + 诊断信号；
- **外环**：读**内环轨迹**，改**策略**（不是改产物）；其诊断信号天然就是内环持续产出的轨迹。
- 两环用同一套纪律（最小改动、门控、死胡同表），只是作用对象不同。

> 关键洞见：**"改产物"与"改指导产物的策略"必须是两个循环、两种节奏**。混在一起会既慢又难归因。

## 2. 泄漏红线 L0 / L1（机械保证泛化）

### 在 ForgeKernel 里
知识被切成三份，**边界即防泄漏的核心**：

| 产物 | 算子专属？ | 含代码？ | 内容 | 谁迭代 |
|---|---|---|---|---|
| 每算子 **milestone** | 是 | 部分（只接口片段，**无实现体**） | 架构决策 / tiling·pipeline 参数 / 目标 | 外环（耗 GPU） |
| **硬件 KB** | **否** | **是（示例代码）** | 硬件接口怎么用（TC/TMA/mbarrier/WGMMA/swizzle） | 跨算子累积 |
| **meta-milestone** | 否 | 否 | 把算子蒸馏成 milestone 的策略与词汇 | 人 + 少量算子样本 |

两条不变量：
- **L0（泄漏边界）**：课程只给"起点 + 决策 + 参数"，**绝不给终点（实现体）**。架构决策/参数可以直接给（那是决策不是代码），参考实现的优化体不行。
- **L1（meta 层算子无关）**：meta 层 harness / prompt **零算子专属信息**；算子相关信息只能作为**运行时输入文件**进。检验法：**换算子时 harness 一个字都不用改**——需要改 = L1 破了。

### 抽象后的一般形态
- **L0 = 教学材料只给"决策与参数"，不给答案本身**。这条让"蒸馏"名副其实：学生必须自己走路径。
- **L1 = 策略层与领域内容严格分离**，且用"开关一个 domain 不需改策略层任何一行"作为**可测的机械判据**。
- 这是"可泛化"的**机械保证**：泛化的是"会备课的老师"（策略 + harness），做某个具体任务时绝不能让它渗进老师本身。

> 关键洞见：可泛化不靠"写得更抽象"，靠**一条能自动检验的边界规则**。

## 3. 机械摘要 + 结构化轨迹（不让 LLM 压缩 LLM 的输入）

### 在 ForgeKernel 里
给外环（meta agent）的默认输入是**结构化轨迹的机械重排**（parser 提取），分两层：

- **Layer 1（默认）= 机械抽取的轨迹摘要**，固定 schema：
  ```
  target/achieved/gap
  curve:       [{iter, metric, verdict}]
  decisions:   [{iter, id, change, correctness, metric_before/after, verdict, binding_constraint}]
  regressions: [{id, symptom, iter, retry_precondition}]        # dead-end table
  profiler:    [{iter, job, binding_constraint, key_metrics, conclusion}]
  milestone_ref + raw_artifact_paths
  ```
- **Layer 2（按需下钻）= 原始产物仅给路径**，meta agent 只在"承重结论需核对"时才拉。

**为什么不用 LLM 预摘要**：真实失败案例——轨迹中途错了结论（"occupancy 墙，只有重 tile 能救"），两轮后才纠正为寄存器溢出；若 meta agent 拿到的是彼时冻结的摘要，就会继承误判。机械抽取只重排**已结构化的字段**、不重新解释，不丢承重信号；LLM 预摘要引入一个有自己判断的过滤器，危险。

**由此而来的硬约束**：内环的轮次记录**必须结构化**（decision id / 前后指标 / verdict / 每轮 binding_constraint / 死胡同表 / NCU 结论），自由文本不可靠解析。实现里 `status.jsonl` 每轮只记**客观事实**（技术、改动、正确性、读数、NCU），**不记**学生的主观分析——让诊断基于硬件事实而非叙事。

### 抽象后的一般形态
- **给 LLM 看的东西，用确定性代码（parser/结构化）去组织，不用另一个 LLM 去压缩。**
- 分层：默认给"机械整理的摘要"，原始数据只给指针，按需下钻。
- 前提：**生产端（内环）必须产出结构化记录**，且只记客观事实、不记自评。

> 关键洞见：**摘要的盲区会变成下游的盲区**；能机械提取就别让 LLM 总结。

## 4. 失败归因到正确产物层

这是四块里最"实"的一块，由四个机制组成。

### 4.1 G / R 二分类诊断
- **G = guidance failure（指导失败：学生动不起来）**
  G1 欠定 / G2 太粗（超出学生能力）/ G3 硬件接口不会（域无关）/ G4 学生噪声
- **R = reach failure（够不着：跟对了但顶不上）**
  R1 地基天花板 / R2 缺一条优化决策

每类有明确的"修复落到哪一层产物"：

| 症状 | 根因 | 修复 | 落地层 |
|---|---|---|---|
| 盲目搜索 / 多步全回退 / 无方向 | G1 欠定 | 加抽象决策 / 加触发条件 | 课程 |
| 步子太大 / 同决策反复错 | G2 太粗 | **拆分**该步 | 课程 |
| 知道要做什么但写不出（不会接口） | G3 接口未知 | 往 KB 加**示例代码** | 知识库 |
| 反复崩正确性 / 心智模型错 | G4 噪声 | 容忍 / 重试，不动课程 | — |
| 跟对了但早早顶住 / 基础值被钉死 | R1 地基天花板 | 松地基决策/参数（结构补丁） | 课程（地基） |
| 全程跟对仍不够 / 参考有而课程缺 | R2 缺决策 | 补上层决策 | 课程 |

辅助信号：正确性是否全程保持、最终性能是否达目标、**性能曲线平滑度**（深谷后回升 / 早顶住 ⇒ 地基顺序错或缺前置决策，R1 的强信号）。

### 4.2 时间相关成本（地基先定）
改第 d 个决策的代价 ≈ 其上已堆叠的内环工作量。所以：
- **外环早期**：还没堆东西，**改地基（M0/M1）最便宜**，且地基定全局天花板 → 一次把结构做对；
- **外环后期**：地基已验，再动=丢弃大量工作 → 转为对上层做**增量/精修**补丁。

规则：外环自己也走 M0→M5 的阶段序——**先锁地基，再往上修**。

### 4.3 死胡同表（负知识持久化）
性能回归 / 补丁回归都记进 dead-end 表，下次诊断**不再提已被否的方向**（`REVERT_PATCH` 并回滚）。

### 4.4 前缀复用 + 决策依赖图
- 每个内环决策是 checkpoint `(课程版本, 轮次快照, git commit)`，按决策 id 索引；
- 每个内环决策记录它依赖哪些课程条目（决策 id）→ **依赖图**；
- 结构补丁命中条目 X ⇒ 从"最早依赖 X 的决策 d*"之前的最后一个有效 checkpoint 恢复，**前缀复用而非从零重跑**；
- 内环要有"从给定 checkpoint 续跑"的入口（不只是从 baseline 起）。

> 关键洞见：**失败要归因到"该改哪一层产物"**（课程 / KB / 重试 / 结构补丁），并用"改得越早越贵"决定优先级，用"死胡同表 + 前缀复用"省算力。

## 5. 附带但通用的两个小设计

- **宽松回退（relaxed revert）**：性能回退不立即严格回退——有些决策是"为后续收益搭的脚手架"，单独启用会先变慢；严格回退会阻止它跨过中间谷底。**但正确性始终是硬门。** 抽象：优化评估要允许"先降后升"，只死守正确性。
- **三线验收（正确性 / 性能 / 机制）**：不把"时间恰好变好"当成功，还要看**目标机制是否真建立**。抽象：区分"结果对"和"机制对"——很多优化偶然变快但机制错，未来会崩。

## 6. 抽象成通用框架的模块划分（落地建议）

把上面四点做成 domain 无关的可复用模块（详见远端 `forge-distill` 仓库）：

| 模块 | 对应设计 | 域无关接口 |
|---|---|---|
| `loops/inner.py` | 双环·内 | 按策略改产物；产出结构化轮次记录 |
| `loops/outer.py` | 双环·外 | 读轨迹，改策略 |
| `boundary.py` | L0/L1 | 校验"策略层无 domain 专属词"；校验"课程不含实现体" |
| `digest.py` | 机械摘要 | 纯函数：结构化轨迹 → Layer-1 digest |
| `diagnose.py` | G/R | 轨迹 → 失败分类 + 落地层 |
| `cost.py` | 时间相关成本 | 决策深度 → 修改代价 |
| `deadends.py` | 死胡同表 | 负知识存取 |
| `resume.py` | 前缀复用 | 依赖图 + checkpoint 恢复点 |

一个**非 GPU 示例**（如"用强模型蒸馏弱模型去解文本组合优化"）即可验证 domain 无关性：换 domain 只改"产物/评估器/参考"，策略层（loops/boundary/digest/diagnose/cost/deadends/resume）一个字不改——这正是 L1 的机械判据。

---

## 7. 一句话总结

ForgeKernel 的可迁移内核是：**内环改产物、外环改策略（双环同构）+ 策略与领域内容硬分离且可机械检验（L0/L1）+ 用确定性代码而非 LLM 去组织喂给 LLM 的轨迹（机械摘要）+ 把失败归因到正确产物层并用依赖图省算力（G/R·成本·死胡同·前缀复用）**。这四点与"GPU/kernel"无关，是任何"强模型蒸馏弱模型做探索"系统的通用骨架。
