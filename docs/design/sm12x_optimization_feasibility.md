# SM12x 优化方案 · 可行性评估

> 评估对象：`SM12x优化方案.md`（6000 Pro 96 GiB / 5000 Pro 72 GiB，SM120/121，原生 FP4，GDDR7，PCIe 无 NVLink）
> 评估依据：本仓库 `porting/6000D/` 实测记录 + `hw_kb/tilelang/sm120/` + `docs/design/megakernel_scheduler_feasibility.md`
> 性质：**静态评估，未在机器上复测**。标「实测」的有本仓库数据支撑，标「需复测」的没有。

## TL;DR

**方案可以执行。** 诊断框架（第 1 节三个检查点）和数据红线（第 6 节）写得可靠，是整份文档最有价值的部分。

需要改三处：

1. **MegaMoE 从「正收益项」降级为「单层内可试」** — 全局 megakernel 在 Qwen3.8 上收益会大幅缩水；
2. **NVFP4 KV 从「优化链最后一环」降级为「未验证项」** — 部署记录里它是风险项，939 ms 那个终点依赖它；
3. **在第 1 节前面加一个前置：测 kernel 间隙占比** — 这个数字决定第 3 节全部算子级优化值不值得做。

另有一条**方案未提但更严重**的事实：这台机器无 NVLink，跨卡 **45 GB/s** 是硬上限。
方案里「通信变瓶颈」的判断成立，且比方案自己说的更严重。

## 1. 方案的优点（先说要保留什么）

### 1.1 三个检查点是全篇最有价值的部分

| 检查点 | 为什么重要 |
|---|---|
| ① 确认后端 W4A4 vs W4A16 | 「FP4 权重 ≠ 跑 W4A4」是真实且高频的坑 |
| ② 检查 PCIe 争用 | 无 NVLink 平台上，拓扑决定一切 |
| ③ 定位关键路径 | 避免「GEMM 加速了但总时间没变」 |

把这三件事放在优化之前，是正确的工程顺序。

### 1.2 数据红线写得准确

五条红线（后端未验不谈 FP4、不跨实验相减、投机按目标并发报告、有损优化必带画质、MegaMoE 计时范围不同）
都是真实的坑。尤其第 5 条——**方案自己承认 1.30–1.41× 非严格同计时**，这个自觉度值得保留。

### 1.3 「顺序不可颠倒」是对的

> 后端不对，后面所有低精度收益都是假的；通信不控，扩 TP 只增加通信开销。

这个判断与实测一致。

## 2. 与本仓库实测的交叉核对

### 2.1 「通信变瓶颈」的判断成立，且实际更严重（实测）

方案引用实验 A：TP2→TP4 后 MoE/Dense **−49%**、Sparse MLA **−37%**，但 AllReduce **+33%**。

本仓库记录（`porting/6000D/RTX6000D_Qwen38FlashNVFP4部署方案.md:153-167`）：

- 2× RTX 6000D，**无 NVLink**，GPU0↔GPU1 = SYS
- 跨卡带宽物理上限 **45 GB/s**
- MoE EP2 all-to-all 已认定为当前瓶颈

两项结论同向，且实测数据说明：**这个瓶颈不是配置问题，是物理上限**。方案里所有依赖「扩并行度提吞吐」的条目都要按这个上限折价。

### 2.2 「Scheduling 轴旋钮无效」已有独立实测（实测）

部署方案 `:153-167` 记录：swizzle / persistent / cluster / CLC 这几个调度轴「从未生效」。

这与方案第 3 节的假设存在张力——方案默认算子级调度仍有优化空间，但本机的实测是
**调度类旋钮在这台卡上普遍无效**。第 3 节的优化应优先选「减少数据移动」类，而非「改调度」类。

## 4. 三处必须修正

### 4.1 MegaMoE 应降级为「单层内可试」

方案把 MegaMoE 列为算子优化的正收益项（单层 1.30–1.41×，SGLang Prefill ≈2×）。

问题不在于数据真假，而在于**它的收益结构在 Qwen3.8 上不成立**：

本仓库对 cohere megakernel 的精读结论（`docs/design/megakernel_scheduler_feasibility.md`）：

> 它最大的收益来源是「消除 wave quantization / backfill」，而这**依赖 parallel transformer layer**——
> attention 与 FFN 从同一 norm 输出出发。源码依据：`decode/schedule.py:1846`，
> 注释 `# Attention and FFN run in parallel and rejoin at rmsnorm.`

而 Qwen3.8 是**串行 48 层**（36 linear_attn + 12 full_attn，`full_attention_interval=4`），没有可 backfill 的空档。

因此 MegaMoE 的可迁移部分只剩：

- ✅ **单层 MoE 内部**：`Copy→GEMM→Copy→GEMM` 共享 SM，省 kernel 切换 —— 这部分成立
- ❌ **跨算子 / 整步融合**：依赖 parallel layer，不成立

方案的实测范围（单层 MoE、SGLang Prefill）恰好落在 ✅ 那部分，所以数据没错；
错的是**推论**——不能从单层收益推出整步收益。

另有一条未计入的风险：batch=8 时 512 experts top-10 只有 80 条 route，
绝大多数 expert 激活 0 次，按 expert 切 row-block 灌满 SM 的调度会大面积空转。

**修正**：把 MegaMoE 标注为「仅单层内实施，不做全局融合」，并加一条前置验证「decode 并发下不回退」。

### 4.2 NVFP4 KV 应降级为未验证项

方案第 2.3 节把 939 ms 作为 TTFT 优化链的终点，最后一环是 **NVFP4 KV**。

本仓库部署记录（`RTX6000D_Qwen38FlashNVFP4部署方案.md:177`）把 `--kv-cache-dtype nvfp4`
列为「省显存 / **可能不兼容崩溃**」的**未测试**项。

**修正**：把 939 ms 标注为「依赖未验证项」，并在链中插入一个「NVFP4 KV 可用性验证」的检查点。
若不通过，该链的终点是 **1.02 s**（fused MoE 那一级）。

### 4.3 缺少「kernel 间隙占比」这个前置

整份方案从通信优化切入，但没有任何一处先量 **kernel 间空隙占总时间的比例**。

这个数字是第 3 节全部工作的门槛：

- 间隙 < 5% → 算子级融合的收益上限就在那里，优先做通信（2.1、2.2）
- 间隙 > 15% → 才值得讨论融合（3.1、3.2）

**修正**：在第 1 节前插入「检查点 ⓪：分段计时，量 kernel 间隙占比」。

## 5. 建议的执行顺序

方案给的是「①后端 → ②通信 → ③算子 → ④调度」，方向正确。建议细化为：

```
⓪ 测 kernel 间隙占比                    ← 新增，决定第 3 节做不做
① 三个检查点（原第 1 节）                ← 不动
② TP2×PP2 拆域（原 2.1）                 ← 首选，收益最确定
③ 细粒度 MoE（原 3.1）                   ← 优先于 MegaMoE
④ CP2×PP4（原 2.3）                      ← 先摘掉 NVFP4 KV 一环
⑤ Two-Batch（原 2.2）                    ← 最后，风险最高
⑥ MegaMoE                                ← 仅单层，且需 decode 不回退验证
```

与方案的差异：

| 变动 | 理由 |
|---|---|
| 新增 ⓪ | 缺这个数字，第 3 节全凭猜测 |
| 3.1 提到 3.2 之前 | 细粒度 MoE 是纯收益且不依赖 megakernel |
| 2.3 挪到 3.1 之后 | 通信拆域（2.1）比 CP×PP（2.3）更简单、收益更确定 |
| 2.2 放到接近最后 | 方案自己标注了退化风险 |
| MegaMoE 放最后 | 收益依赖模型结构，需单独验证 |

## 6. 需要补充的实验

| 实验 | 目的 | 判定标准 |
|---|---|---|
| kernel 间隙占比 | 决定算子级优化是否值得做 | 分段计时，间隙 / 总时间 |
| NVFP4 KV 可用性 | 解锁 939 ms 终点 | 能否稳定跑通，不崩 |
| MegaMoE @ decode 并发 | 验证是否回退 | 低并发 TPOT 不劣于基线 |
| DSpark5 复现 | 核实 3.32× | 独立复现，同作业对照 |
| Two-Batch 组合矩阵 | 找出退化边界 | TP2/TP4 × W4A4/W4A16 × chunk 8192/4096 |

## 7. 一句话结论

**方案可执行**，诊断框架与数据红线是可靠的资产。

需要的是**三处降级 + 一个前置**：MegaMoE 降为单层内可试、NVFP4 KV 降为未验证、
在开头补一个 kernel 间隙测量。

最根本的一条外部约束未被方案提及但决定一切：**这台机器无 NVLink，跨卡 45 GB/s**。
所有「扩并行度」类优化都必须按这个物理上限折价。
