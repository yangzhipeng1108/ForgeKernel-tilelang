# ForgeKernel 官方介绍文 · 摘要整理

> 来源：知乎文章《ForgeKernel 项目介绍》（https://zhuanlan.zhihu.com/p/2103990232068665648）。
> 本文只是对该文内容的提炼，不含本仓库的实测结论。凡文中未提及的内容，本文不补。

## 1. 项目是什么

ForgeKernel 是面壁智能（ModelBench 智能进化实验室）联合 OpenBMB 开源的**自进化 GPU kernel Agent**。
它把「写一个比专家库更快的 kernel」重构为三段分离：

| 角色 | 做什么 |
|---|---|
| **Teacher**（arch agent） | 只通过 running / timing / profiling 读懂参照 kernel，蒸馏成「架构优先」的 milestone 课程 |
| **Student**（coding agent） | 看不到参照源码，按课程逐决策实现 |
| **参照晋升** | 每个被接受的最优 kernel 封装为下一轮的参照 |

经硬件探针验证的结论沉淀进**跨算子共享的硬件知识库**。

**成绩**（文中表述）：Hopper + Blackwell 27 个算子，追平或超过 22 个专家库 kernel 中的 18 个
（对手含 FlashAttention-4、cuDNN、DeepGEMM、FlashMLA）；追平或超过三个 kernel 生成系统的全部 7 个 kernel；
最高 **+170.6%**，几何平均 **+39.4%**。2026-10 登顶 CANN-Bench（950DT / 950PR / A3）与
NVIDIA SOL-ExecBench 的 FlashInfer-Bench。22.5 小时公开直播中，零参考源码把 DeepSeek-V4.1
FlashMLA Prefill 写快 **9.8%**（518µs → 472µs）。

**重要限定**：开源版本目前只支持 NVIDIA Hopper（sm90）与 Blackwell（sm100）；昇腾成绩是团队内部适配，代码与 KB 未随仓库开源。

## 3. 背景：为什么做这个

GPU kernel 是大模型效率的最终瓶颈，也是最稀缺的人力。FlashAttention 这类顶级 kernel 一次架构级迭代
往往需要资深专家数月。团队称如今「AI 超越最佳人类实现的算子优化任务，最多只需两天」。

国产芯片的痛点更直接：追赶 NVIDIA 的难点不在硬件指标，而在 CUDA 生态十几年的专家经验与软件分层。

**赛道现状的三个问题**：

1. 评测基线参差——很多工作对比 PyTorch eager / torch.compile，而非 FlashAttention-4、DeepGEMM 这类专家库；
2. 迭代只在单次运行内——没有跨运行的参照晋升与持续进化；
3. 经验以模型权重或单次上下文存在——缺少可审计、可认证、可跨算子复用的显式知识。

**三条现有路线的空档**：

| 路线 | 代表 | 空档 |
|---|---|---|
| 编译器/自动调度 | torch.compile、Triton autotune、Ansor | 搜索空间受模板限制，难做架构级重写 |
| 训练专用模型 | Kevin、CUDA Agent、ConCuR、TritonRL | 训练成本高、迭代慢，换硬件/模型需重训 |
| 免训练 Agent | Astra、KernelAgent、CudaForge、K-Search、KDA、JustGoal | 多为一次性搜索，架构易锁死，经验不沉淀 |

## 4. 三条解法

### 4.1 架构角色分离 + 课程蒸馏

针对「结构选择过早锁死」：通用 coding agent 能修编译错误、改 tile，但容易早期选定一个结构后，
把全部预算花在该结构内部的微调上。而 kernel 的规律是**结构决定上限，参数调优只吃剩余小收益**。

做法：Teacher 通过运行、计时、NCU 剖析逆向出 kernel 拆分、tile 形状、warp 分工、资源预算，
组织成 milestone 课程；最容易错、改动代价最大的决策在 **M0** 全部定下并冻结，`M1→Mk` 只在既定结构内调杠杆。

### 4.2 探针认证的跨算子知识库

针对「经验没有跨任务积累」：入库纪律是**只收硬件机制、不收算子算法**；每条自包含、可运行、带来源；
证据链按读者分层——agent 只能看官方文档 / 公开 API / 本仓库探针，参照实现的痕迹进入仅供人审的
provenance 层，由 lint 机械把守。

### 4.3 参照晋升的自进化链

针对「超过基线就停」：每个通过确认的最优 kernel 被密封晋升为下一代的参照，目标设为它的 **1.05×**（默认步长），
循环直到单代提升落入同作业计时噪声地板（离散度，**至少 1.5%**）之内。

## 6. 整体架构：双层闭环 + 两个积累

```
变异 → 选择 → 保留 → 棘轮
```

| 循环 | 改变的对象 | 主要反馈 | 时间范围 |
|---|---|---|---|
| 绿色内层（Student） | 当前 kernel 的代码与实施参数 | 编译、正确性、计时、机制观测 | 一项或一组决策 |
| 紫色外层（Teacher） | 当前任务的 milestone，必要时补 KB | 内层轨迹、卡点、收益实验 | 一个执行段或课程修订 |
| 橙色参照晋升 | 下一代任务的参照与目标 | confirmed best、确认增益 | 多次 campaign |
| 蓝色知识积累 | 条件化的硬件接口配方 | probe 或符合规范的机制证据 | 多个算子与任务 |

**这张图最重要的设计**：把失败路由到正确的层级。

| 标记 | 路径 | 实际改变什么 | 成本 |
|---|---|---|---|
| ① fail | 返回实现 | 修当前方案的落实 | 局部、可回滚、便宜 |
| ② plateau | 返回分析与蒸馏 | 修搜索方向、粒度或地基 | 全局、会作废下游检查点 |
| ③ pass | 进入交付出口 | 保存满足条件的结果 | — |
| 橙色虚线 | Shipped → Reference | 把对手换成上一代最好版本 | 整代重新开始、最贵 |

三件事的变更成本差几个数量级，若把「学生写不出来」误判成「课程欠定」就会频繁重蒸；反之则原地重试、永远平台。
**这三个回路本质上是三种失败的分诊机制。**

## 7. 从第一性原理出发

### 7.1 GPU 优化是在多种约束间取舍

四类因素：计算、数据移动、时间依赖、有限资源。性能来自一条多层映射链：
语义契约 → 算法与计算图 → 数据布局和时间调度 → 源程序 → 机器指令 → 硬件执行与测量。

耦合的例子：中间结果留寄存器可省 smem 搬运，但存活过多会 spill 反而变慢；增加流水 stage 可提前备数据，
但也增加 smem 占用与同步开销、降低并发。

**所以优化的对象首先是结构和条件，而参数值不是首要对象。**

### 7.2 不同决策的「改动半径」极不对称

改一个 wait_group 深度是局部改动；改 tile 形状牵连寄存器预算、smem 布局、流水深度、epilogue；
改 kernel 拆分或数据流则让下游几乎全部作废。

因此优化是在一个**承诺层级**里搜索：M0 定义「架构固定 + 第一个可运行版本」，
后续在结构内做增量优化。但这套承诺必须能被证据推翻——冻结不是永久禁止变化，
而是**禁止 Student 把地基变化藏在后期普通调参里**。

### 7.3 编码 agent 是「有界理性」的

上下文、耐心、预算都有限，倾向用最小可归因的修改解决缺陷，在有限尝试里抓一个看起来可行的架构再微调。
所以不能让 agent 直接面对整个架构空间，**搜索要被课程约束**——这是 Teacher/Student 分离的根源。

### 7.4 硬件机制可迁移，算子算法不可迁移

TMA 怎么用、mbarrier 的 parity 怎么设、WGMMA 的 A 操作数怎么从寄存器喂——这些在 attention、GEMM、conv
里反复出现；但「这个算子的 5 个 GEMM 怎么连」换个算子就不成立。

**可积累的是硬件机制，不是算法——这是知识库能成立的物理基础。**

## 8. 两类记忆

- **性能记忆**：被确认的最优 kernel 密封，晋升为下一轮参照，目标设为它的 1.05×；
- **机制记忆**：GPU probe 认证过的硬件机制写进 `hw_kb/`，按语言 × 架构组织，跨算子复用。

## 9. 三层产物

| 产物 | 算子相关 | 含代码 | 内容 | 谁迭代 | 生命周期 |
|---|---|---|---|---|---|
| 单算子 milestone | 是 | 仅契约/接口片段，**无实现体** | 架构决策、tile/流水参数、依赖、成本、目标、死路表 | 外层 meta 循环 | 一次运行 |
| `hw_kb/` | 否 | 是（示例代码） | TMA / mbarrier / WGMMA / UMMA / swizzle 等机制用法 | 跨算子积累 | 跨运行、跨算子 |
| meta-milestone | 否 | 否 | 课程语法 + 诊断学 + 补丁经济学 | 人 + 少量算子样本 | 跨版本 |

### 两条不变量

- **L0（泄漏红线）**：milestone 给「起点 + 决策 + 参数」，永远不给终点。任何 kernel 实现体
  （包括 M0 的架构）都不得出现，尤其禁止把 oracle 的实现逐字、改名或逐行转写后放进去。
- **L1（meta agent 算子无关）**：Teacher 的 harness 代码与 prompt 必须携带零算子信息。
  `flash_attn`、`softmax`、`tile_m` 这类词出现在 harness 或 system prompt 里即违规；
  一切算子信息只能作为运行时输入文件进入。**换算子时 meta 侧一行不改；要改就说明 L1 破了。**

## 10. 决策五元组

| 字段 | 回答的问题 | 避免的问题 |
|---|---|---|
| **Action** | 做什么（一句话，不写具体 shape 数值） | 只有愿景没有行动 |
| **Purpose** | 消除哪个瓶颈、满足哪个约束（不能只写"为了更快"） | 为了采用某技术而采用它 |
| **Trigger condition** | 在哪些症状/条件/形状范围下做 | 把条件性技巧当通用规律 |
| **Cost** | 寄存器、smem、同步、接口等代价 | 只记收益不记副作用 |
| **Depends on** | 上游依赖、耦合组与前置关系 | 忽略前提、错误复用旧实现 |

文中示例：「增加流水 stage」不是完整决策，还要说明当前存在未覆盖的供给延迟、资源有余量、
供给与消费粒度匹配、额外 buffer 占用、验收时检查实际重叠和总时间。

**Depends on 的三个符号**：

| 符号 | 含义 | 进 DAG |
|---|---|---|
| `⇐` | 派生自谁（上游） | 是，是边 |
| `⊗` | 必须与谁同一 commit 落地（同伴） | 否，记为 companion group |
| `⇒` | 是谁的前置（下游） | 否，只为人读 |

依赖图的作用：**改一个决策，沿 `⇐` 边就能算出哪些下游作废、从哪里续跑**——这是前缀复用与 in-place reopen 的基础。

## 11. 诊断分类：G / R

```
学生卡住
 ├─ 下一步没完成（G）
 │    ├─ 缺目标/触发 → G1 → milestone（加决策）
 │    ├─ 缺分辨率     → G2 → milestone（拆细）
 │    ├─ 缺机制       → G3 → KB（补接口）
 │    └─ 执行噪声     → G4 → 不改（容忍/重试）
 └─ 下一步完成了，但没到 target（R）
      ├─ 天花板太低   → R1 → milestone 地基（松结构，贵）
      └─ 路径缺一段   → R2 → milestone（加决策，便宜）
```

一个学生要完成一步需要三样东西：**目标**（做什么、何时做）、**分辨率**（这一步够小）、**机制**（硬件上怎么实现）。
缺哪样对应一个 G 子类；三样都有还失败就是噪声。

| 诊断 | 目的地 | 成本 |
|---|---|---|
| G1 欠定 | milestone | 低（additive） |
| G2 过粗 | milestone | 中（split） |
| G3 接口未知 | KB | 低（跨算子复用） |
| G4 学生噪声 | 不改 | ≈0 |
| R1 地基天花板 | milestone 地基 | 高（structural） |
| R2 缺决策 | milestone | 低（additive） |
| 老师误诊 | meta-milestone / diagnose prompt | 高（影响所有算子） |

**这张表的意义：三类产物不是三个仓库，而是三个「诊断目的地」。**
目的地错了，补丁就打错地方——G3 打到 milestone 会让 milestone 变成架构说明书，换算子即失效；
G1 打到 KB 会让 KB 塞进算子算法，失去复用性。

**补丁经济学**：有读数支持改善则保留；有可归因证据但无改善则回退；读数不足或耦合包未完成则暂缓判断。
原则是尽量用最小、可归因的修改解决缺陷，并保留仍然有效的成果。

## 12. 算子 milestone 的标准框架

`operators/<op>/milestone.md` 的七节：

| 节 | 回答的问题 | 为什么必须机器检查 |
|---|---|---|
| 0. Problem statement and target | 算什么、在什么硬件、目标多少 | `target_ms` 是停止条件的 SSOT |
| 1. Problem contract (Math Spec) | 数学语义是什么 | 防止把实现选择偷渡进契约 |
| 2. Decision DAG + phase order | 先做什么后做什么、谁依赖谁 | 补丁靠它算失效范围 |
| 3. Decision details | 每个决策的五元组 + 每阶段 Gate | 没有五元组学生不知做什么/何时做/代价 |
| 4. Known dead ends | 哪些路走过是死的 | 防止重复踩坑 |
| 5. Global correctness/performance gate | 全局容差 + 各性能信号健康标准 | 防止"局部 PASS、全局错" |
| 6. Rules | 交付粒度、标记纪律、反抄袭、INFEASIBLE | gate 的「法律依据」 |
| 7. Decision tree quick reference | 可选速查 | 不校验，纯人类可读 |
| Worked Example | — | **唯一允许放具体 shape 值的地方** |

M0 Gate 有特殊边界：以正确性、架构符合和机制为主，**没有绝对毫秒性能门槛**。
所以不能理解成「每个 M 都必须立刻比参考更快」。

## 13. hw_kb 的组织方式

按 `(语言, 架构)` 切片：

```
hw_kb/
  cutedsl/   README.md  TEMPLATE.md  sm90/  sm100/
  cuda/      README.md  TEMPLATE.md  sm100/     # 只有 sm100，没有 sm90
```

- **语言轴**：同一套硬件，两种抽象、两套 intrinsic、两个编译器；
- **架构轴**：同一门语言，两代指令集（WGMMA vs tcgen05/UMMA、TMA 能力、TMEM、cluster 行为都不同）。

一条 recipe 的完整类型是 `(mechanism, language, architecture)`，例如：

- `(wgmma_deferred_wait, cutedsl, sm90)`
- `(tcgen05_umma_issue_cta_pair, cutedsl, sm100)`
- `(mbarrier_wait_encoding, cuda, sm100)`

**一次 run 只读写一棵树**：CuTe DSL + sm90 的运行只读 `hw_kb/cutedsl/sm90/`，
不能读 `cuda/sm100` 来给 CuTe DSL 用，也不能读 `cutedsl/sm90` 给 B200 用。

每条 entry 五节固定格式：`Purpose` / `When needed (trigger)` / `Minimal runnable example` /
`Gotchas` / `Sources`（只许官方文档、公共 infra API、本仓库 probe）。

## 14. 一次完整示例（文中的示意）

> 假设优化一个矩阵计算任务。

1. **分析参考**：发现 tensor 活跃不足，但不直接断言 HBM 是瓶颈，提出「供给与消费重叠不足 +
   寄存器存活量限制前瞻」的假设。
2. **构造课程**：M0 规定 tile、生产者/消费者角色、buffer 所有权、供给消费粒度、寄存器与 smem 预算；
   M1+ 安排计划内流水实验，写明触发、代价和机制预测。
3. **实现**：查 KB 完成同步接口；地址映射写错 → 走 ① 修代码。
4. **阶段验收**：地址修对、计时改善，但机制观测显示重叠没建立 → **不能把「时间恰好更好」当作目标机制成功**。
5. **遇到平台**：② 让 Teacher 读整段轨迹；只是不会接口走 G3，驻留策略成天花板走 R1。
6. **重开受影响部分**：按 DAG 重做真正依赖它的决策，复用仍有效的代码与证据。
7. **确认交付**：确认最好 SHA 与性能，输出 shipped kernel 和报告。
8. **分别积累**：完整实现进下一代 reference；通用同步机制进 KB，接受归属审阅。

## 15. 一句话总结

ForgeKernel 把「写快 kernel」重构为「**把专家经验转成可执行、可验证、可修订的决策路径**」：
Teacher 用测量而非源码定架构，Student 在课程内实现，Gate 三线验收（正确性/性能/机制），
失败按 G/R 分诊到正确的产物层，确认的最优解晋升为下一轮对手，
可迁移的硬件机制沉淀为跨算子复用的知识。
