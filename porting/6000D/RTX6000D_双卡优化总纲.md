# RTX 6000D ×2 双卡优化总纲（一页表）

> 本机实测汇总。全部数字在 2× RTX 6000D 上测得（无 NVLink，GPU0↔GPU1 = SYS），
> 两卡 SM 均已锁 2000 MHz，`NCCL_P2P_LEVEL=SYS`，`NCCL_ALGO=Tree`（除注明）。
> 详细推导与逐项实测见同目录 `RTX6000D_双卡调度准备.md`。

## 0. 一句话结论

**跨卡 45 GB/s（无 NVLink）是硬天花板。能接近 2× 的方案是"零通信的 DP"和"层边界通信的 PP"；
TP 只在大 K 成立；1F1B 与调度技巧在纯 Python 下无效。** 这一切与单卡 KB 的
"重排调度轴从不生效"同源——差异只在**绑定资源是跨卡带宽**而非 SM/DRAM。

## 1. 硬件基线（决定一切）

| 项 | 实测 | 含义 |
|---|---|---|
| NVLink | 无（两卡均不支持） | 无 GPU 直连 |
| 拓扑 GPU0↔GPU1 | **SYS**（PCIe + 跨 NUMA） | 最慢路径，连同一 PCIe 桥都不是 |
| 裸 peer copy | **45.2** 单向 / **91.3** 双向 GB/s | PCIe 5.0 物理上限，无可挖（见附录 A） |
| NCCL all-reduce（Tree/Ring） | **34.2 / 32.3 GB/s** | 集合通信税，≈裸单向 75% |
| 跨卡延迟（P2P / host） | **0.5 µs / 20 µs** | 小消息是延迟受限，P2P 快 38× |
| NCCL all-reduce（无 P2P_LEVEL） | 12.5 GB/s | **默认会降级 SHM，必须设 SYS，否则慢 3×** |
| all-reduce fp16 vs fp32 | 472 vs 973 µs @ 8M | 减字节有效，但端到端收益小（见 §4） |
| 单卡 fp16 GEMM | 155 TF | 基线 |
| 6× mlx5 IB 网卡 | 闲置 | 设计意图是多机，单机双卡是最小拓扑 |

## 2. 四种范式速查

| 范式 | 适用 | 实测加速 | 关键 |
|---|---|---|---|
| **DP**（数据并行，零通信） | 模型放得进单卡 | 纯 GEMM **1.9×**；训练 1.6–1.9× | 首选；通信为 0 |
| **PP**（流水线，层边界通信） | 层能均分到两卡 | 2 层参考 **2.90×**；微批趋近 **1.8×** | 次选；通信量小 |
| **TP**（张量并行，每层 all-reduce） | 必须切权重 | 大 K **1.65×**；方阵 **全亏** | 仅大 K；见 §3 判据 |
| **1F1B 微批流水** | —— | **更慢（0.46×–0.38×）** | 纯 Python 做不了 |

## 3. 决策树

```
模型能放进单卡（89GB）吗？
├─ 能 ─→ 路线 A: DP（零通信）
│         ├─ 纯 GEMM：大问题 ~1.9×，小问题 ~1.5×（launch 开销摊薄）
│         └─ 训练闭环：分桶+反向重叠，大模型 ~1.9×，小模型 ~1.6×
├─ 不能 ─→
│         ├─ 层能均分到两卡 → 路线 C: PP（首选，2 层 2.9×，微批趋近 1.8×）
│         └─ 必须切权重 → 路线 B: TP（有条件）
│              ⚠️ export NCCL_P2P_LEVEL=SYS（否则 all-reduce 12.5 GB/s）
│              判据：2MNK/155T > MN·2/34.5G 才赚 —— 仅大 K（如 65536）
│              方阵 4k³/8k³ 全亏（0.39×/0.66×）
└─ 跨机 → 走 IB（6× mlx5），不是本题范围
```

## 4. 已系统扫过、各自的天花板

| 轴 | 结果 | 结论 |
|---|---|---|
| DP 纯 GEMM | 4k³ 1.53–1.71× → 6k/8k³ **1.92–1.94×** | 越大越线性，差距是 launch 开销 |
| DP 训练（朴素逐参数 all-reduce） | 1.41–1.44× | 太慢，被分桶取代 |
| DP 训练（**分桶+反向重叠**） | d=512 **1.55×**，d=768 **1.77×**，d=1536 L=8 **1.87–1.90×** | **大模型逼近 2×** |
| 分桶大小 | 1–16 MB 扫遍，8 MB 最优 | 已到边际 |
| fp16/bf16 梯度归约 | 裸 all-reduce 快 2×，端到端仅 **+1.6%** | 仅大模型微利 |
| `NCCL_ALGO=Tree` | 909 vs Ring 973 µs | **+7%**，已设默认 |
| PP 无微批（2 层） | **2.90×** | 层各占一卡，天然并行 |
| PP 微批 | 2L 1.37× → 8L **1.69×** | 层越多 bubble 越小 |
| PP CUDA stream+event 重叠 | 8L **1.75–1.79×**，16L 崩 0.86× | 纯 Python 天花板 ~1.8× |
| TP over K | 4096³ 0.39×、8192³ 0.66×、**8192×4096×65536 1.65×**、16384×4096×16384 1.07× | compute/comm 比决定 |
| TP 分块 overlap | 4096³ 0.20→0.18×（更差） | 分块让 AR 次数 ×CH，赔 |
| 1F1B 微批 | ×2 13.39ms、×4 23.82ms vs 基线 9.14ms | **纯 Python 更慢** |

## 5. 为什么要重叠也到顶了（定量）

小模型 d=512 L=4（分桶重叠基线 8.75–9.14 ms）：

| 成分 | 时间 | 占比 |
|---|---|---|
| fwd + bwd | 6.41 ms | —— |
| 梯度 all-reduce（55 MB） | 1.48 ms | 23% |
| **完美重叠理论下限** | **max(6.41, 1.48) = 6.41 ms** | —— |
| 分桶重叠实测 | 8.75 ms | —— |

剩余 8.75→6.4 ms 的差距来自**反向尾部**：最后一个桶的通信无计算可藏。
再压只能消除通信本身（更少卡/更小模型），**不是调度能解决的**。

## 6. 必须踩的坑（否则数字全错）

1. **`NCCL_P2P_LEVEL=SYS`**——不设则 NCCL 降级 SHM，all-reduce 12.5 GB/s（慢 3×）。
2. **两卡都锁频**——只锁 GPU0 时 GPU1 空转 195 MHz，并发 scaling 假偏低。
3. **分桶 all_reduce 前必须 `comm.wait_stream(compute)`**——否则读到半写入的 flat buffer，weight drift 从 0 变 1e-2。
4. **TileLang kernel 不传播 autograd**（编译产物 `requires_grad=False`）——直接接进训练会"权重无梯度、forward 白跑"，得到假的快速度数。必须用 `torch.autograd.Function` 包 forward、backward 走 torch matmul。
5. **TileLang JIT 在 `torch.cuda.graph` capture 期间失败**（`cudaErrorStreamCaptureInvalidated`）——双卡别直接上 graph。
6. **DDP 正确性靠 weight drift 校验**——各卡吃不同数据 + 梯度 all-reduce 后，`drift=0.00` 才算真同步。

## 8. 底线

1. **单机双卡可挖的轴已系统穷尽**：DP / PP / TP / 重叠 / 1F1B / 桶调优 / 算法 / dtype 全部实测。
2. **加速天花板**：纯 GEMM DP **1.9×**、大模型训练 DP **1.9×**、小模型训练 **1.6×**、PP **1.8–2.9×**。
3. **结构性上限是无 NVLink 的 45 GB/s**——与单卡 KB "重排轴从不生效"同源。
4. **想更多只有三条路**：用更大的模型（自然逼近 2×）、PP 分担放不下的模型、跨机 IB 扩展。

## 附录 A：跨卡带宽全景（三种测法，量的是不同东西）

同一台机器、同一锁频下，三个工具给出三个数——**都正确，量的是不同层**：

| 工具 / 测法 | 结果 | 量的是什么 | 能否优化 |
|---|---|---|---|
| `p2pBandwidthLatencyTest`（裸 P2P copy） | **45.2 / 45.5** 单向、**91.3** 双向 GB/s | 硬件 P2P 拷贝上限 | ❌ PCIe 5.0 硬顶（~70% 效率） |
| `all_reduce_perf`（NCCL Tree，1GB） | **34.2 GB/s** | 集合通信（求和+广播） | ❌ 算法税，≈ 裸单向 75% |
| `all_reduce_perf`（NCCL Ring，1GB） | 32.3 GB/s | 集合通信（Ring） | ❌ 比 Tree 慢 7% |
| NCCL 默认（不设 P2P_LEVEL） | 12.4 GB/s | **SHM 降级**（走 host） | ✅ 设 `NCCL_P2P_LEVEL=SYS` 修复 |

**为什么裸拷贝 45 > all-reduce 34**：all-reduce 是"求和 + 广播"，有归约算法开销，
永远低于裸拷贝；34/45 = 75% 是正常效率。

**延迟才是小消息命门（比带宽更值得关注）**：

| 路径 | 跨卡延迟 | 说明 |
|---|---|---|
| P2P 直连 | **0.50–0.56 µs** | 启用 P2P |
| host 中转（SHM） | **19.5–21.3 µs** | 慢 **~38×** |

所以 `NCCL_P2P_LEVEL=SYS` 对小消息（decode、小 all-reduce）的收益 **远大于** 大消息——
小张量是延迟受限，不是带宽受限。

**锁频对带宽几乎无影响（45.19 vs 45.20），但稳定延迟/小消息**；工具自身也提示
"Results may vary when GPU Boost is enabled"。

### A.1 正确测法（`sudo` 会吞环境变量！）

```bash
# ❌ 错误：export 在 shell，sudo 清空环境 -> NCCL 回退 SHM，只有 12 GB/s
export NCCL_P2P_LEVEL=SYS; sudo ./all_reduce_perf ...

# ✅ 正确：env 放在 sudo 之后（用 sudo -E 或 env 前缀均可传递变量）
sudo env \
  NCCL_P2P_LEVEL=SYS NCCL_IB_DISABLE=1 NCCL_P2P_DISABLE=0 NCCL_ALGO=Tree \
  ./all_reduce_perf -b 128M -e 1G -f 2 -g 2      # 预期 Avg bus ≈ 34 GB/s

# 裸 P2P 拷贝上限（45 GB/s 的出处）
sudo <cuda-samples>/p2pBandwidthLatencyTest   # 先两卡锁频
```

`NCCL_DEBUG=INFO` 可确认：日志出现 `NCCL_P2P_LEVEL set by environment to SYS`
且不再有 `via SHM/direct`。
