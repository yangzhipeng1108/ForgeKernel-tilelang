# 双卡调度与优化：准备清单与实测基线（RTX 6000D ×2）

> 本文件是**工程规划 + 实测基线**，不是 KB recipe（recipe 只记单卡接口事实）。
> 全部数字在本机实测，SM 时钟已锁 2000 MHz（两卡）。

## 一、这台机器的硬约束（决定一切）

| 事实 | 实测值 | 影响 |
|---|---|---|
| 无 NVLink | `nvidia-smi nvlink -s` → "Device does not have or support Nvlink" | 无 GPU 直连高带宽 |
| 两卡拓扑 | `topo -m`: GPU0↔GPU1 = **SYS** | 走 PCIe + NUMA SMP 最慢路径，连同一 PCIe 桥都不是 |
| P2P 可用 | `can_device_access_peer` 双向 True | 可 P2P 拷贝，但… |
| **P2P 带宽** | **45 GB/s 单向 / 90 GB/s 聚合** | 对比单卡内 642 GB/s → **跨卡只有单卡的 1/14** |
| 单卡峰值 | fp16 GEMM 155–156 TF；HBM 读 1145 GB/s | 锁频后 |
| TileLang 多卡 API | **无**（0.1.15 无 NCCL/distributed/comm，只有 3rdparty TVM disco 未暴露） | 多卡必须靠 torch 编排 |

**核心判断：这机器没有 NVLink、跨卡 45 GB/s，任何"频繁跨卡通信"的方案都会被互联打死。** 双卡只在**粗粒度、低通信**的场景有意义。

## 二、两条可行路线（按通信量从低到高）

### 路线 A：数据并行 DP（推荐，零跨卡通信）

把不同 batch/样本分给两卡，各跑各的，**只在最后或偶尔同步**（如参数更新、loss 汇总）。

- **实测（锁两卡频后）**：

  | 问题尺寸 | 模式 | scaling |
  |---|---|---|
  | 4k³ | 两卡独立全量 | 1.71× |
  | 4k³ | N 切半（DP） | 1.53× |
  | 6k³ | 两卡独立全量 | 1.94× |
  | 8k³ | 两卡独立全量 | 1.94× |
  | 8k³ | N 切半（DP） | 1.92× |

- **关键修正**：早期在 4k³ 上测到 1.53–1.71×，一度误判为"两卡共享 NUMA 的硬件串扰"。放大到 6k³/8k³ 后 scaling 升到 **1.92–1.94×**——真正的主因是 **kernel launch 开销在小问题上占比过高**（每次 `kernel(...)` 的 Python+dispatch 固定成本被摊薄），**不是硬件串扰**。问题越大越接近线性。
- **结论**：DP 是这台机器**唯一稳赚**的双卡方式，零通信，**大问题接近 1.9×**；只有很小的问题才会掉到 1.5×。可用 `scripts/dual_gpu_bench.py` 自行测量。

### 路线 B：张量并行 TP / 模型并行（有条件可行，关键看 compute/comm 比）

把权重切到两卡、每层做 all-reduce/all-gather。**每层都要跨卡通信。**

**必须先设一个开关**：`export NCCL_P2P_LEVEL=SYS`。
⚠️ **这是本机多卡最重要的一条**：不加它，NCCL 判定 GPU0↔GPU1 跨 NUMA 后**自动降级到 host SHM/direct 路径**，实测 all-reduce 只有 **12.5 GB/s**；加上 `NCCL_P2P_LEVEL=SYS` 后 NCCL 走 CUDA P2P，all-reduce 升到 **34.5 GB/s（2.8×）**，broadcast 达 **45 GB/s**（接近裸 P2P 上限）。`NCCL_DEBUG=INFO` 可看到从 `via SHM/direct` 变为走 P2P。

**实测 NCCL 集合通信带宽（2 卡，P2P_LEVEL=SYS）**：

| 消息 | all-reduce | all-gather | broadcast |
|---|---|---|---|
| 1 MB | 21.8 GB/s | 22.8 | 36.4 |
| 8 MB | 33.2 | 30.5 | 43.6 |
| 32 MB | 34.4 | 31.2 | 44.6 |
| 128 MB | 31.9 | 30.0 | 44.8 |

**实测 TP（over K，all-reduce 求和）真机结果**：

| 形状 | 单卡 | TP(2) | 加速 | cos |
|---|---|---|---|---|
| 4096³ | 887 µs | 2250 µs | **0.39×** | 1.0 |
| 8192³ | 6984 µs | 10631 µs | **0.66×** | 1.0 |
| 8192×4096×65536 | 31331 µs | 18972 µs | **1.65×** | 1.0 |
| 16384×4096×16384 | 16124 µs | 15108 µs | 1.07× | 1.0 |

- **结论修正**：TP 不是"完全不可行"，而是**由 compute/comm 比决定**。判据：`(flop/155TFlops) / (M×N×2 bytes / 34.5GB/s) > 1` 才赚。
  - **大 K、小 M×N（如 K=65536）能赚到 1.6×+**（K 大 → 计算多而 comm 固定为 M×N）。
  - 常规方阵（4k³/8k³）**全亏**（comm 比计算还大）。
- 记账要点：all-reduce 的通信量是 **M×N（输出大小）**，与 K **无关**；而计算量是 2·M·N·K。所以**堆 K 是 TP 的增益来源**——这正是大 K 形状赢、方阵输的根因。
- **overlap 实测（把 K 再分块、计算与 all-reduce 交错）反而更差**：

  | 形状 | 单卡 | TP 串行 | TP overlap（分块）|
  |---|---|---|---|
  | 4096³ | 895 µs | 4406 µs (0.20×) | 4946 µs (0.18×) |
  | 8192³ | 7774 µs | 21004 µs (0.37×) | 20818 µs (0.37×) |
  | 8192×4096×65536 | 31757 µs | 26177 µs (1.21×) | 24150 µs (1.31×) |

  **根因**：把 K 分 CH 块做流水，会让 all-reduce 从 1 次变成 CH 次，**通信总量 ×CH**，overlap 省下的时间远小于额外通信成本。只有大 K 情形勉强正收益（1.21→1.31×）。**结论：TP 不该分块 overlap，用单次 all-reduce 即可。**

### 路线 C：流水线并行 PP（中等，本机表现好）

按层切分到两卡，只在层边界传 activation。

- 通信量 = 层边界 activation（batch×seq×hidden），远小于 TP 的每层权重 all-reduce。
- **实测（2 层 GEMM 参考，无微批）**：单卡串行两层 2069 µs → PP 两卡各算一层 **713 µs = 2.90×**。超 2× 是因为参照是单卡算两层之和，PP 让两卡各算一层真并行。
- **微批流水实测（4k² 层，M=4096）**：

  | 层数 | 微批数 | 单卡全跑 | PP 微批 | 加速 |
  |---|---|---|---|---|
  | 2 | 2 | 2016 µs | 1469 µs | 1.37× |
  | 4 | 4 | 3989 µs | 2456 µs | 1.62× |
  | 8 | 8 | 8170 µs | 4837 µs | **1.69×** |

  层越多、微批越多，bubble 占比越小，趋近 **1.69×**（仍不到 2×）。
- **异步 send/recv 未能救回**：改用 `isend/irecv` 后 8 层仍 1.67×，16 层反而崩到 **0.85×**。根因：Python 侧发出 `isend` 时 GPU 计算已在默认流上串行完成。
- **CUDA stream + event 真重叠**：把计算放 comp stream、p2p 放 comm stream，用 event 串联后，8 层从 1.69× 提到 **1.75–1.79×**（稳定），但 **16 层/16 微批仍崩到 0.86×**——微批过多时事件链开销 + NCCL 通信本身成为瓶颈。
- **结论**：PP 是本机除 DP 外**最划算**的双卡方式。**层能均分到两卡时用 PP**；纯 Python 编排的天花板约 **1.8×**，要逼近 2× 须靠 DeepSpeed/Megatron 的工业级流水实现。

### 真实模型接入（DP 训练闭环，实测）

用纯 PyTorch 手写微型 GPT（attention+FFN+LayerNorm，fwd+bwd+AdamW，每步 DDP 梯度 all-reduce）再接 TileLang GEMM，`scripts/train_dp.py`。

**真 DDP**：每卡用**不同的数据**（per-rank generator 模拟 DistributedSampler），梯度 all-reduce 后各卡权重必须一致——实测 **weight drift max = 0.00e+00**，证明同步正确。

**⚠️ 一个必须先纠正的假象**：TileLang kernel **不传播 autograd**（编译产物 `requires_grad=False`、`grad_fn=None`）。最初直接把 `tilelang.compile` 的输出接进训练，forward 走了但**该层权重根本拿不到梯度**，测出的"TileLang 每步 5.9 ms（快 1.64×）"是**假的**——那几步其实没反传。正确做法：用 `torch.autograd.Function` 包住 TileLang forward、backward 用 torch matmul（`scripts/train_dp.py::_GemmFn`）。

**修正后的诚实数据（梯度分桶 + 反向重叠 DDP）**：

| 模型 | 每步（torch）| 每步（TileLang）| DP 吞吐 scaling |
|---|---|---|---|
| d=512 L=4 | 8.6 ms | 8.2 ms | 1.57×（torch）/ 1.53×（tl）|
| d=768 L=4 | 14.9 ms | 13.8 ms | 1.77×（torch）/ 1.70×（tl）|

- **TileLang 与 cuBLAS 基本持平**（8.2 vs 8.6 ms）——之前"完胜"是 autograd 缺失导致的假象。小模型上两者相当。
- **梯度分桶 + 反向重叠把 DP scaling 从 1.41×（朴素逐参数 all-reduce）提到 1.57×（d=512）/ 1.77×（d=768）**，drift 仍 0.00。模型越大、通信占比越高，重叠收益越大。离 2× 的剩余差距是通信本身（34.5 GB/s）。
- 分桶实现要点：每个桶的梯度就绪即在 comm stream 上 all_reduce，但**必须先 `comm.wait_stream(compute)` 保证 flat buffer 写完**，否则读到半写入值（这是把 drift 从 0 变成 1e-2 的真实 bug，已修）。

## 三、实现前必须准备的东西

### 1. 环境/硬件准备（硬性）

- [ ] **两卡都锁频**：`sudo nvidia-smi -i 0 -lgc 2000,2000` **和** `-i 1 -lgc 2000,2000`。
      ⚠️ 实测：只锁 GPU0 时 GPU1 空转在 195 MHz，并发测出 1.69× 的**假偏低**；两卡都锁后才准。
- [ ] 确认 PCIe 链路：`nvidia-smi --query-gpu=index,pcie.link.gen.current,pcie.link.width.current`
      （本机 GPU1 曾显示 gen1×16，若长期 gen1 需查 BIOS/插槽）。
- [ ] 认命无 NVLink：不要找 NVLink 相关优化，方案按 45 GB/s 设计。

### 2. 进程模型（必须二选一，先定）

| 模型 | 适用 | 说明 |
|---|---|---|
| **单进程 + 多线程 + `torch.cuda.set_device`** | DP、探针、小规模 | 最简单；threaded 并发实测大问题 1.94×。Python GIL 只在 launch 时短暂占用，GEMM 期间释放，实测不成为瓶颈 |
| **多进程 + `torchrun --nproc_per_node 2` + `torch.distributed`(NCCL)** | 真实训练/TP/PP | 每个 rank 绑一张卡。**必须 `export NCCL_P2P_LEVEL=SYS`**，否则 NCCL 降级到 SHM（all-reduce 12.5 GB/s）；加后走 P2P（34.5 GB/s）。这是生产路径 |

TileLang kernel 本身**无多卡概念**，靠 `torch.cuda.set_device(d)` + 当前 stream 绑定到卡。所以：
- DP：两个线程/进程各自 `set_device`，各跑 `kernel(...)`，零通信。
- TP/PP：kernel 之外用 `torch.distributed.all_reduce/all_gather` 做通信（NCCL backend）。

### 3. 通信原语与后端

- [ ] `torch.distributed` + **NCCL backend**，并**必须 `export NCCL_P2P_LEVEL=SYS`**（否则降级 SHM，all-reduce 掉到 12.5 GB/s）。
- [ ] 用 `NCCL_DEBUG=INFO` 验证走的是 P2P 而非 `via SHM/direct`。
- [ ] 想清楚**通信拓扑**：本机两卡 SYS 路径对称，无 NVSwitch，ring 就是单向 45 GB/s；all-reduce 实用 34.5 GB/s。
- [ ] 用 `torch.cuda.Stream` 让通信与计算**重叠**（TP 的关键，本骨架未做）。
- [ ] 通信量预算：每层 all-reduce 字节 = **输出 M×N×2 字节**（与 K 无关）× 34.5 GB/s，对比该层计算 `2MNK/155TFlops`，ratio < 1 才值得 TP。

### 4. 计时/正确性方法（沿用单卡纪律）

- [ ] **两卡都锁频**后再计时（否则 ±20% 假信号）。
- [ ] 并发计时用**每卡独立 CUDA Event**，各线程 `en.synchronize()` 后取 `max` 作为该轮耗时。
- [ ] ⚠️ **TileLang JIT 调用在 `torch.cuda.graph` capture 期间会失败**（实测 `cudaErrorStreamCaptureInvalidated`）——双卡 CUDA graph 需用 TileLang 的 graph 支持或预热后手动 capture，否则别用 graph。
- [ ] 验证跨卡正确性：`md` / cosine 对比单卡结果。

## 四、决策树

```
模型能放进单卡（89GB）吗？
├─ 能，且想加速吞吐 → 路线 A: DP
│    ├─ 零通信，大问题约 1.9×，极小问题 1.5×（launch 开销摊薄）
│    └─ 准备：两卡锁频、线程/进程各 set_device、各跑各的
├─ 不能，单卡放不下 →
│    ├─ 层数多、能均分到两卡 → 路线 C: PP（首选，实测 2.90× 无 bubble）
│    └─ 层很宽、必须切权重 → 路线 B: TP（有条件）
│         ⚠️ 先 export NCCL_P2P_LEVEL=SYS，否则 all-reduce 只有 12.5 GB/s
│         判据：2MNK/155T > MN*2/34.5G 才赚 —— 只在大 K（如 65536）成立
│         方阵 4k³/8k³ 全亏（0.39× / 0.66×）
└─ 只是想"用两张卡跑两个实验" → 直接 DP，8k³ 可到 1.9×
```

## 五、底线结论

1. **无 NVLink + 45 GB/s SYS 互联；NCCL 必须 `NCCL_P2P_LEVEL=SYS` 才走 P2P（否则 SHM，all-reduce 12.5 vs 34.5 GB/s）。**
2. **DP 零通信、随问题增大逼近线性**：纯 GEMM 6k³/8k³ 达 **1.92–1.94×**；训练闭环（含梯度同步）用**分桶+重叠**达 **1.57–1.77×**（朴素逐参数只有 1.41–1.44×）。
3. **PP 是除 DP 外最划算**：层边界通信量小、天然并行；无微批 2 层参考 **2.90×**，微批随层数趋近 **1.69×**。适合层能均分到两卡。
4. **TP 有条件可行**：能否赚只看 compute/comm 比。**大 K（65536）赚 1.65×；方阵 4k³/8k³ 全亏（0.39×/0.66×）**。判据 `2MNK/155T > MN·2/34.5G`。
5. **TP 不要分块 overlap**：分块让 all-reduce 次数 ×CH、通信总量翻倍，实测反而更差（4096³ 0.20→0.18×）；用单次 all-reduce。PP 的 Python 级 `isend` 也不能真重叠（16 层崩到 0.85×），真重叠需框架级 CUDA stream 编排。
6. **带宽是硬顶**：裸 peer copy 44.7 GB/s、NCCL all-reduce 34.5 GB/s，都贴着 45 GB/s 的物理上限，无可挖空间。裸 all-reduce fp16/bf16 比 fp32 快 **2×**（472 vs 973 µs @ 8M），但**端到端收益很小**：重叠已把通信藏进计算后，减字节意义有限——大模型（d=1536 L=8）fp32 **1.87×** vs fp16 **1.90×**（仅 +1.6%）。
7. **模型越大 DP 越接近 2×**：d=1536 L=8 用分桶重叠达 **1.87–1.90×**，而 d=512 只有 1.55–1.57×。计算占比越高、通信越容易被藏住。
8. **NCCL 算法可调**：`NCCL_ALGO=Tree` 比 Ring 快 **7%**（909 vs 973 µs @ 32MB），已设为脚本默认。
8. 实现前**必须先做**：两卡锁频、`NCCL_P2P_LEVEL=SYS`、定进程模型（线程 DP / 多进程 NCCL）、算通信预算。
9. 手工直写跨卡 TileLang kernel（自己管 P2P 拷贝）**不被现有 API 支持**——0.1.15 无 comm 原语，只能在 kernel 外用 torch.distributed 编排。
10. 现成工具（`scripts/`）：
   - `dual_gpu_bench.py`：单进程多线程 DP 骨架（`--mode full|dp --check`）。
   - `nccl_gemm_bench.py`：多进程 NCCL 骨架（`--mode tp|pp --nlayer --microbatch`）。
   - `train_dp.py`：真实模型 DP 训练闭环（微型 GPT，分桶重叠 DDP，`--use-tilelang --check --no-overlap`）。

## 五之二、双卡还有优化空间吗？（系统判断）

**结论：结构性空间已基本挖尽，剩余是"边际优化"，不是"翻倍"。** 逐条：

| 方向 | 还有空间？ | 依据 |
|---|---|---|
| 提升跨卡带宽 | **否（硬顶）** | 裸 peer copy 44.7 GB/s = 物理上限，无 NVLink |
| NCCL 配置 | **少量（~7%）** | `NCCL_P2P_LEVEL=SYS`（已必用，3×）；`NCCL_ALGO=Tree` 再 +7% |
| 减通信字节（fp16 梯度） | **有，但仅通信主导时** | fp16 归约快 2×；小模型重叠后≈0，大模型 +3.6% 且随规模增大 |
| 通信-计算重叠 | **已基本到位** | 分桶+反向重叠已把 DP 从 1.41→1.57–1.90×；1F1B 微批实测更慢，纯 Python 到头 |
| 调度/编排技巧 | **否** | 与单卡 KB 同结论：重排轴无跨 block/跨卡局部性可赚 |
| 换范式 | **是唯一大空间** | 模型单卡放不下时 PP（2.9×）；放得下就 DP（1.9× GEMM / 1.6-1.8× 训练）|

**还能做的具体事（按性价比）**：
1. **大模型才值得的 fp16/bf16 梯度归约**——`train_dp.py --reduce-dtype`，通信量减半；小模型别开（无收益还可能损精度）。
2. **`NCCL_ALGO=Tree`**——已设为 `train_dp.py` 默认，稳定 +7%。
3. **真实多机**：6 张 mlx5 IB 网卡闲置——跨机扩展才是这机器设计意图，单机双卡本就是最小拓扑。

### 1F1B 微批流水：实测为负结果（已试）

把 batch 拆成微批、让一个微批的 forward 与另一个的 backward 重叠（工业 1F1B）：

| 方案 | 每步 | 结论 |
|---|---|---|
| 单批 + 分桶重叠（基线）| 9.14 ms | — |
| 1F1B 微批×2 | 13.39 ms | **更慢 46%** |
| 1F1B 微批×4 | 23.82 ms | **更慢 2.6×** |

**为什么 Python 版 1F1B 反而更慢**：微批拆小后单个 GEMM 效率暴跌（launch 开销占比暴涨），且梯度累加是串行的；Python 无法让 forward/backward 真正跨微批并发（kernel launch 在 host 线程同步推进）。**纯 Python 做不了工业 1F1B**，必须靠 DeepSpeed/Megatron 的 C++ 调度。

### 为什么分桶重叠已到天花板（定量）

这个模型 **fwd+bwd 6.41 ms，梯度 all-reduce 仅 1.48 ms（占 23%）**。即便**完美重叠**，理论下限就是 `max(6.41, 1.48)=6.41 ms`——当前分桶重叠已达 **8.75 ms**（桶大小 8MB 最优，扫 1–16MB 都一样），说明**通信已基本藏进计算，剩余 8.75→6.4 ms 的差距来自反向尾部**：反向传播的最后一个桶的通信没东西可藏。要再压只能把通信完全消掉（更少的卡/更小的模型），不是调度能解决的。

**一句话**：单机双卡在现有硬件的加速天花板约 **DP 1.9×（GEMM）/ 1.6–1.8×（训练）**，已摸到；真要更多只能靠**更大模型让通信占比下降**、**PP 分担放不下的模型**、或**跨机 IB 扩展**。

## 六、实测数据存档（本机，锁频 2000）

| 测试 | 结果 |
|---|---|
